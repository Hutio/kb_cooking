# 데이터 뷰 (개요)

> 다른 지도가 사람이 손으로 엮은 색인이라면, 여기 있는 `.base` 파일은 frontmatter 를 직접 질의한다. 문서를 고치면 표가 따라 바뀌고, 새 문서를 추가하면 조건에 맞는 순간 저절로 끼어든다.

## 시작하기

Bases 는 Obsidian 1.9 부터 코어 기능이라 플러그인 설치가 필요 없다. `.base` 파일을 클릭하면 표가 열리고, 상단 탭으로 뷰를 바꾼다. 열 머리글을 눌러 정렬하거나 필터를 더하는 것은 파일을 건드리지 않고도 된다.

찾는 것이 무엇이냐에 따라 들어갈 곳이 다르다.

| 지금 궁금한 것 | 열 파일 |
|---|---|
| 30분 안에 뭘 만들지 | [[빠른 요리.base]] |
| 장 봐 온 걸 어디에 넣고 언제까지 쓰는지 | [[재료 보관.base]] |
| 이달에 뭐가 제철인지 | [[제철 재료.base]] |
| 만들 수 있는 요리 전체를 조건으로 훑기 | [[레시피 전체.base]] |
| 오늘 담가야 다음 주에 먹는 것 | [[숙성이 필요한 것.base]] |

## 전체 목록

각 파일이 잡는 문서 수는 2026-08-29 기준이다. 조건에 맞는 문서가 늘면 자동으로 커진다.

| 파일 | 조건 | 문서 수 | 뷰 |
|---|---|---|---|
| [[빠른 요리.base]] | recipe · time_total ≤ 30 | 57 | 빠른 순 · 계열별 · 15분 이내 |
| [[재료 보관.base]] | ingredient 전체 | 152 | 분류별 · 보관 온도대별 · 냉장 먼저 쓸 것 |
| [[제철 재료.base]] | ingredient · season 있음 | 50 | 분류별 · 제철 표기순 |
| [[레시피 전체.base]] | recipe 전체 | 167 | 계열별 · 난이도별 · 오래 걸리는 순 · 최근 갱신순 |
| [[숙성이 필요한 것.base]] | recipe · aging 있음, 또는 발효·염지 기법 | 14 | 전체 · 유형별 |

### 지도 문서

`.base` 가 property 로 기계적으로 거른 목록이라면, 지도는 **사람이 하나의 축으로 엮은 색인**이다. 같은 폴더에 두는 이유가 여기 있다 — 둘 다 폴더 구조를 가로지른다.

- [[발효 (지도)]] — 미생물·염도·온도. 김치·장·치즈·빵이 왜 같은 기술인지
- [[감칠맛 급원 (지도)]] — 글루탐산·이노신산·구아닐산의 상승효과
- [[냉동 보관 (지도)]] — 얼음 결정이 조직에 하는 일
- [[제철 (지도)]] — 월별. 이달에 무엇을 사고 무엇을 저장할지

### 빠른 요리

`time_total` 이 30 이하인 레시피다. 총 시간과 손 가는 시간을 나란히 놓은 이유는 둘이 크게 벌어지는 요리가 따로 있기 때문이다 — 총 30분이어도 손은 5분만 가면 평일 저녁에 쓸 수 있다. `15분 이내` 뷰에 걸리는 11건은 대부분 나물 무침과 소스라, 메인이 아니라 한 접시를 채우는 용도로 본다.

### 재료 보관

이 볼트에서 가장 실용적인 표다. `storage`(온도대) · `storage_short`(단기) · `storage_long`(장기) 세 필드를 한 줄에 놓으면, 장 보고 돌아와 봉투를 풀면서 무엇을 냉장 안쪽에 넣고 무엇을 그날 안에 써야 하는지가 한눈에 잡힌다. `냉장 먼저 쓸 것` 뷰는 `storage` 가 냉장 계열인 75건만 남긴다.

### 제철 재료

`season` 이 적힌 50건이다. [[제철 (지도)]] 가 월별로 손수 엮은 색인이라면 이쪽은 원본 필드를 그대로 보여 준다. 제철 표기가 `9~11월` 처럼 자유 문자열이라 월 단위 정렬은 되지 않는다 — 분류별로 묶어 놓고 눈으로 훑는 쓰임이다.

### 레시피 전체

마스터 표다. 계열·분류·인분·시간·난이도가 모두 열로 있어, 파일을 고치지 않고도 열 머리글에서 조건을 바꿔 가며 좁힐 수 있다. `최근 갱신순` 뷰는 `updated` 내림차순 40건으로 잘라 두었다. 재정비 작업이 어디까지 왔는지 확인하는 용도다.

### 숙성이 필요한 것

시간이 일을 대신하는 문서를 모았다. `aging` 필드가 붙은 레시피 12건은 전부 김치·장아찌·청 계열이고, 여기에 기법 문서 [[발효]] 와 [[염지]] 를 더해 14건이다. **`aging` 은 "언제 먹을 수 있는가"가 아니라 "언제부터 언제까지 담가 두는가"를 적는 필드다** — 실온 며칠 + 냉장 며칠 형태로 쓰여 있어, 담그는 날을 역산할 수 있다.

## property 설계

Bases 가 질의할 수 있는 것은 frontmatter 에 실제로 들어 있는 값뿐이다. 이 볼트는 규약(CLAUDE.md §3)이 type 별 필수 필드를 강제해 왔기 때문에 누락이 없고, 그래서 필터가 성립한다.

| property | type | 값의 성격 | 질의에서 쓰는 방식 |
|---|---|---|---|
| `type` | 전체 | 6종 고정 (recipe/ingredient/technique/taste/tool/index) | 모든 base 의 1차 필터 |
| `time_total` `time_active` | recipe | 정수(분) | 부등호 비교·정렬 |
| `servings` | recipe | 정수 | 정렬 |
| `cuisine` `category` `difficulty` | recipe | 닫힌 어휘 | 그룹화 |
| `aging` | recipe | 자유 문자열, 12건에만 존재 | 존재 여부로 필터 |
| `group` | ingredient/technique/tool | 닫힌 어휘 | 그룹화 |
| `storage` | ingredient | 온도대 조합 문자열 | 그룹화·동등 비교 |
| `storage_short` `storage_long` | ingredient | 한 줄 요약 문장 | 표시 전용 |
| `season` | ingredient | 자유 문자열, 50건에만 존재 | 존재 여부로 필터 |
| `updated` | 전체 | YYYY-MM-DD | 내림차순 정렬 |

**정수로 쓴 필드만 부등호가 먹는다.** `time_total: 30` 이어야 `<= 30` 이 성립하고, `time_total: "30분"` 이면 문자열 비교가 되어 조용히 틀린다. 시간·인분을 단위 없는 숫자로 못 박아 둔 규약이 여기서 값을 한다.

반대로 `season` 과 `aging` 은 자유 문자열이라 크기 비교가 안 된다. 그래서 이 둘은 `file.hasProperty()` 로 **있는지 없는지만** 묻고, 내용은 사람이 읽는다. 월별 정렬이 필요하면 별도의 숫자 필드를 새로 만들어야 하는데, 그 값은 아직 없다.

### 문법 메모

`.base` 는 YAML 이다. 뷰마다 `type`(table 또는 cards)과 `name` 이 **둘 다 필수**고, 하나라도 빠지면 파일이 열리지 않는다. 필터는 문자열 한 줄이거나 `and`/`or`/`not` **한 개만** 가진 객체여야 하며, 그 값은 반드시 배열이다.

property 를 가리킬 때 접두사가 없으면 `note.` 이 붙은 것으로 해석된다. 즉 `cuisine` 과 `note.cuisine` 은 같다. 파일 자체의 속성은 `file.name`, `file.mtime` 처럼 `file.` 을 붙인다. 이 볼트의 base 파일은 헷갈리지 않도록 전부 `note.` 을 명시해 두었다.

정렬은 `sort`(항목마다 `property` + `direction: ASC|DESC`)이고, `order` 는 정렬이 아니라 **열 순서**다. 이름이 비슷해 자주 뒤바뀐다.
